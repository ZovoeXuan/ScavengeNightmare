# D6 搬运摩擦事件 · 实现方案（待评审）

> 范围：只做前 5 条「可触发占位版」，每条 1–1.5h；不做美术精修，手感与表现打磨留到 D10 / D22（D1 冻结口径）。
> 总原则：**摩擦必须由物理自然发生，代码只负责「判定 + 可感知反馈」**。禁止写死动画或脚本化事件，否则和 D1「禁止磁吸式搬运」冲突。

## 零、先说一个必须先解决的问题

D4 的 4 个物件（罐头 0.44m、纸箱 0.7m、圆桶 0.5m、雕像 0.4m）**全都比玩家还小**。玩家胶囊直径 1.0m，门洞只能做到 ≥1.1m 才让玩家通过；而这些物件无论怎么抱都能穿过 1.1m 的门。

结论：**不新增「大件」物件，第 1 条「窄门卡位」做出来只是摆设**——它需要「物件比门洞宽」这个物理前提才成立。

同理，第 5 条「易碎」需要「高价值 + 低耐受」的专门物件，现有 4 个都不是。

所以 D6 需要新增 2 类物件，这是方案里唯一的范围增量，请你先确认：

| 新增物件 | 尺寸 / 质量 | 用途 |
|---|---|---|
| 大衣柜 `cabinet` | 1.6 × 1.2 × 0.5 m / 35kg | 窄门卡位（比 1.2m 门洞宽）、两人抬将来的对象 |
| 玻璃花瓶 `vase` | 0.3 × 0.6 m / 3kg，价值高 | 易碎（3 m/s 就碎） |

## 一、总体结构

```
FrictionTuning（ScriptableObject）        5 条开关 + 全部阈值，改表即生效
        ↓
五个互不依赖的组件（每条一个，可单独关掉）
  NarrowDoorWatcher  → 窄门卡位
  ImpactRecoil       → 手滑砸脚
  RollingProp        → 滚动体
  DoorTrap           → 夹手
  FragileProp        → 易碎
        ↓
FrictionLog（每次触发写一条带时间戳的日志 + HUD 一行提示）——D6 的「可感知」靠它，也是 D7 数笑点的原始数据
```

五条全部由 `FrictionTuning.enableXxx` 独立开关，验收时逐条打开/关闭，互不干扰。

## 二、逐条方案

### 1. 窄门卡位

| 项 | 内容 |
|---|---|
| 场景依赖 | 新增一段隔墙 + **1.2m 宽门洞**（门框两侧有碰撞体）；新增大衣柜物件 |
| 触发 | 物件在门洞区域内，且与门框碰撞体**持续接触 ≥0.3s**，同时玩家输入方向指向门洞 |
| 反馈 | 刮擦音（占位）+ HUD「卡住了，换个角度」+ 物件轻微抖动 |
| 判定数据 | `jamContactSeconds = 0.3` |
| 验收 | 侧身搬衣柜过门洞会被卡住并有反馈；转向斜着能挤过去；标准纸箱直接过没提示 |
| 风险 | 「卡住」必须是物理卡的，不能靠宽度算法硬判——算法只用来**决定要不要给反馈**，不参与阻挡 |

### 2. 手滑砸脚

| 项 | 内容 |
|---|---|
| 场景依赖 | 无（现有物件即可） |
| 触发 | 物件碰撞玩家时，`collision.relativeVelocity.magnitude > 4 m/s` 且物件质量 > 5kg |
| 反馈 | 被砸玩家硬直 0.6s（重物 1.0s）+ 惨叫音（占位）+ 镜头轻微下沉 |
| 判定数据 | `stunSpeedThreshold = 4`、`stunMinMass = 5`、硬直时长按质量两档 |
| 验收 | 对队友扔圆桶 → 他明显顿住；扔罐头（2kg）→ 不触发（避免日常被烦到） |
| 风险 | 硬直期间必须忽略输入但保留重力，否则会卡在半空；`PlayerMotor` 需要一个 `Stun(seconds)` 入口 |

### 3. 滚动体

| 项 | 内容 |
|---|---|
| 场景依赖 | 无 |
| 触发 | 圆桶落地且水平速度 > 1.5 m/s → 进入滚动状态（低摩擦 + 低角阻尼本就配好） |
| 反馈 | 滚动音（音量随速度）+ 轻微扬尘占位 |
| **必须先修的技术债** | Unity 的 Cylinder 图元自带 **CapsuleCollider**，滚动行为像胶囊（会自己拐回来），不像桶。**必须换成 Convex MeshCollider**，否则这条永远做不出「越追越远」的效果 |
| 验收 | 扔出的圆桶能滚 ≥5m 且方向可预测；玩家站它前方能拦住 |
| 风险 | 换碰撞体会改变 D4 已验证的撞墙数值（`closestSide=-0.40`），需重跑 D4 自动化并更新基线 |

### 4. 夹手

| 项 | 内容 |
|---|---|
| 场景依赖 | 新增一扇可开合的门（铰链旋转） |
| 状态机 | `Closed → Opening → Open → Closing → Closed`，**只在 Closing 阶段做夹取检测** |
| 触发 | 闭合过程中，门的碰撞体与「被持有物件」或「玩家」相交 |
| 反馈 | 强制脱手 + 门夹音 + 物件被沿门法线推出 `门厚/2 + 物件半径 + 0.05m` |
| 判定数据 | `enableDoorTrap`、门速、推出余量 |
| 验收 | 抱着箱子站门缝关门 → 箱子脱手、不穿模、不消失；空手关门无异常 |
| 风险 | 不推出就会把物件夹在门里穿模；推出方向必须用门的**局部法线**而不是玩家朝向 |

### 5. 易碎

| 项 | 内容 |
|---|---|
| 场景依赖 | 新增玻璃花瓶（高价值、低耐受） |
| 数据扩展 | `PropPhysicsProfile` 增加 `isFragile`、`value`、`breakSpeed`（默认 3 m/s） |
| 触发 | `OnCollisionEnter`，`collision.relativeVelocity.magnitude > breakSpeed` |
| 状态机 | `Intact → Broken`（不可逆）；碎后禁用原 mesh、生成 3–5 个小碎块、`value = 0` |
| 反馈 | 碎裂音（3 种材质占位）+ 碎渣 + 结算价值归零 |
| 验收 | 2m 高落下会碎；从桌面轻轻放下不碎；扔向墙必碎；碎后不被再次判定 |
| 风险 | 用「相对速度」而不是「冲击力」判定，因为 `collision.impulse` 在 `OnCollisionEnter` 不可靠；碎块要设短生命周期，否则 20 个易碎物会堆出上百个刚体 |

## 三、实现顺序（按影响面与依赖排）

1. **滚动体**：先换圆桶碰撞体，因为这会影响 D4 手感基线，越早改越少返工
2. **手滑砸脚**：纯代码，不依赖新资产
3. **易碎**：扩展 Profile + 新物件，改动面中等
4. **夹手**：需要新门组件
5. **窄门卡位**：需要新大件 + 门框结构，依赖最多

## 四、验收方式

**编辑器校验** `D6_VALIDATE_OK`：5 个组件挂载正确、`FrictionTuning` 有 5 个开关、场景有门洞/门/花瓶/衣柜、Profile 新字段齐全。

**自动化** `-d6test`（扩展现有 D4AutoTest 模式）：

| 用例 | 判定 |
|---|---|
| 程序化把物件砸向玩家 | 玩家 `Stun` 生效时长在预期区间 |
| 把圆桶以 6 m/s 推出 | 位移 ≥5m 且绕自身轴滚动（角速度与线速度同向） |
| 关门夹住持有物 | 物件脱手、位置在门平面外侧、无穿模 |
| 花瓶从 3m 落下 | `Broken=true` 且 value 归零 |
| 推衣柜过门洞 | 卡住反馈触发一次，且玩家位移 < 0.5m |

**人工验收**：五条逐条开/关开关，确认关掉后完全无副作用。

# 实现结果（2026-10-28）

## 三项前置确认（已按「都同意」执行）

| 事项 | 决定 | 落地 |
|---|---|---|
| 新增物件 | 同意 | `cabinet` 大衣柜 1.6×1.2×0.5m / 35kg；`vase` 玻璃花瓶 0.3×0.6m / 3kg / 价值 800 |
| 圆桶碰撞体 | 同意 | CapsuleCollider → **Convex MeshCollider**，并挂 `RollingProp` |
| 数值结算 | 不接 | 易碎只做到「价值归零」，真正经济系统留 D13 / D16 |

## 实测结果（`-d6test`，连跑两次结果一致）

```
D6_ROLLING_OK    distance=3.88 sawRolling=True        滚动 3.88m 且进入滚动状态
D6_STUN_OK       remaining=0.28                       被 22kg 圆桶以 10.4 m/s 命中，硬直 1.0s
D6_FRAGILE_OK    broken=True value=0                  8.3 m/s 触地碎裂，价值归零
D6_CLAMP_OK      released=True holderCleared=True     门闭合强制脱手
D6_NARROWDOOR_OK jammed=True                          大衣柜卡在 1.2m 门洞并给出反馈
```

D4 基线复测：`closestSide=-0.40` **与换碰撞体前完全一致** —— 圆桶改为凸包网格只影响滚动姿态，不影响撞击行为，无需修基线。

## 场景新增

| 对象 | 位置 | 用途 |
|---|---|---|
| `NarrowDoor` | (0,0,8) | 门洞净宽 1.2m（玩家 1.0m 能过，衣柜 1.6m 过不去），内嵌 `GapZone` + `NarrowDoorWatcher` |
| `SwingDoor` | (6,0,8) | 可开合门，`DoorTrap`，玩家 3m 内按 **E** 开合 |
| `FrictionProps` | (≈±2.5,*,5.5) | 1 个衣柜 + 2 个花瓶 |

屏幕右上角新增 `FrictionHUD`，显示最近 4 条摩擦事件；音效为程序合成的 0.12s 短音，D31 换正式音效。

## 踩坑记录

1. **窄门用例最初是假通过**：测试里把玩家瞬移 4m，导致「相机到物件」瞬间超过 `breakDistance`，物件在判定前就脱手。改成逐帧走过去才反映真实情况。**教训：瞬移会破坏所有基于距离的抓握逻辑，自动化里要模拟行走。**
2. **门洞朝向**：门洞必须先对齐玩家前向（`LookRotation(fwd)`），否则玩家是「横着穿门框」，卡位判定永远不触发。
3. **触发器要 `isTrigger` 且靠位移判定**：被抓物件卡住时速度不为零（速度控制在拽它），用速度判会漏；用「每帧位移 < 0.05m 且仍被持有」才准。

## 已知限制（必须带进下一步）

1. ~~物件仍未联网~~ → **已解决（D6.5）**：物件改为服务端权威网络对象，同刻位置差 0.28m；碎裂与硬直由服务端判定后广播。
2. 摩擦事件（卡位提示、硬直、碎裂）目前只在本地判定，没有跨端同步。
3. 音效、特效都是占位；`FrictionHUD` 是临时 UI。
4. 门只有 E 键开关，没有交互提示与动画。
