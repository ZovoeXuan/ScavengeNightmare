# D12 · 1 号图「废弃超市」白盒

> 计划原文：设计 1 号图（废弃超市）白盒布局：约 40×40m；2-3 条主路径；至少 2 个窄门、1 段楼梯；3 个拾荒区（货架区 / 仓库区 / 收银区）；1 个撤离点（后门）；3-5 个怪物巡逻锚点；给出俯视坐标平面图。
> 验收：可进图拾荒、动线合理、窄门与楼梯可用。

---

## 一、首要决定：新建场景，不动 Main

`Main.unity` 是 20×20m 沙盒，D3/D4/D6/D8/D9 **全部自动化用例的基线**。在它上面改地图会一次性废掉所有回归。

所以：

| 场景 | 角色 |
|---|---|
| `Main.unity` | 沙盒基线，只服务自动化验收，**不改动** |
| `Supermarket.unity` | 1 号图白盒，服务「进图拾荒、动线、窄门楼梯」 |

做法不是从零搭，而是**复制 Main 的配置骨架**（NetworkManager / SteamLobby / TraitBootstrap / HUD / 平行光），清掉沙盒几何体，按平面图坐标重建。这样联机、身份、抓取、UI 全部继承，不用重配一遍引用。

打包：`BuildWindows.Build` 默认打 Main（既有流程零改动），加 `-map=supermarket` 打超市图到独立目录 `Builds/Supermarket/`——**输出目录分开，否则验完白盒会冲掉测试基线包**。

## 二、布局（40×40m，x 向右、z 向上，原点中心）

| 要素 | 坐标 |
|---|---|
| 入口（前门） | z=+20，开口 x ∈ [-3, 3] |
| 撤离点（后门） | z=-20，开口 x ∈ [-2, 2]；撤离区 (0, -18.5) 4×2.6m |
| 货架区 | x ∈ [-10, 3]，z ∈ [2, 15]，4 排 13m 货架，排间 2.2m 通道 |
| 仓库区 | x ∈ [-20, -11]，z ∈ [-14, -2]，5 处堆垛 |
| 收银区 | x ∈ [8, 18]，z ∈ [0, 4]，4 台收银台 |
| 中央主通道 | x ∈ [4, 8]，贯穿南北 |
| 窄门 A（仓库入口） | x=-11，z=-6，1.2m |
| 窄门 B（后门通道） | z=-14，x=0，1.2m |
| 楼梯 | x=16.5，z=-7 → -11.2，12 级 ×0.25m = 3.0m |
| 夹层 | x ∈ [11, 19]，z ∈ [-14, -11.4]，高 3.0m，带护栏 |
| 出生点 ×4 | z=17，x = -4 / -1.3 / 1.3 / 4 |
| 巡逻锚点 ×5 | 货架(0,8)、收银(12,2)、仓库(-15,-8)、后门(0,-17)、楼梯(16,-5) |

**三条主路径**：中央直穿（入口→主通道→窄门 B→后门）、西绕行（入口→西通道→窄门 A→仓库→后门）、东绕行（入口→东通道→收银→楼梯口→后门）。

**货物分布刻意做成「越值钱的越难搬」**：花瓶在收银台（要穿过货架迷宫），雕像在仓库深处（要过窄门 A 才能运出）。

## 三、物件锚点：替代硬编码坐标表

原来 `PropSpawner` 用组件里的一张 `entries` 坐标表——那是 Main 沙盒专用的，换图就要改组件配置。

改为 `PropSpawnAnchor`：场景里摆点、只写物件档 id，`PropSpawner` 自动从 `NetworkManager.spawnPrefabs` 里按档匹配 prefab。

- 有锚点 → 按锚点生成（新图都走这条）
- **没锚点 → 回退 `entries`**（Main 沙盒与全部既有用例不受影响，这点必须保持）

本图 18 个锚点：货架 8（罐头/花瓶/纸箱）、仓库 6（圆桶/衣柜/雕像）、收银 4（花瓶/罐头/纸箱），覆盖全部 6 个物件档。

## 五、过程中修掉的一个隐蔽缺陷（值得记住）

现象：Setup 报「5 个巡逻锚点」，Validate 却只找到 1 个，**而且每次剩下的是哪一个都不一样**。

根因：一个 `.cs` 里放多个 `MonoBehaviour` 时，Unity 用「文件 guid + **类专属本地 fileID**」定位脚本。文件的第一个类用 `11500000`，后续类各有自己的 fileID。序列化时退化成了只有本地 fileID、没有 guid 的形式，重开场景就解析不到。

中间踩了两次坑：

1. 一开始把所有退化引用**统一改写成 `11500000 + guid`** → 5 个巡逻锚点 + 1 个撤离区**全被解析成第一个类**，变成「24 个道具锚点、0 个巡逻锚点」。
2. 改成保留原 fileID 只补 guid → 保留的是从 Main 复制来的**陈旧 ID**，仍然 0 个。

最终解法是消除问题本身：**每个类拆成独立文件**，各自是文件主类，Unity 天然写成标准形式。修完 `repaired=0`（不再需要修复），连续两次校验都是 5/5。

另外两个配套教训：
- **改场景文件前必须先关场景**：场景留在内存里时，后续 `Refresh` 或编辑器退出会用内存旧数据再写一次盘，把文本修复覆盖掉。
- **别信内存里的数量**：Setup 曾报 5 个而 Validate 读到 1 个。统计要放在重新打开场景之后。

## 七、已知限制

1. **撤离点只做进入检测与日志**，不结算、不加 UI——结算属于 D13 的物件系统。
2. **巡逻锚点只摆位**，D14 才实现状态机读取。
3. **白盒材质为纯色 URP/Lit**，无贴图无光照烘焙；正式美术在 D16 之后。
4. **夹层只做了 2.6m 进深的平台**（楼梯顶端接平台南缘），不是完整二层——白盒阶段只验证「楼梯能上、能站住」。
5. **动线合理性目前只有坐标推演 + 单机冒烟**，没有真人跑图验证；是否绕路、是否会卡在货架之间，要等 D7 实测时一并看。
